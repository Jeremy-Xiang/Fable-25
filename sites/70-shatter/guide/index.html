SHATTER

A hero word that's actually made of the pixels it was drawn with

01 The idea

Most "particle text" demos on the web fake it — a pre-baked list of points shaped roughly like letters. SHATTER seeds its particles from the real rendered glyphs: the word is drawn once to an invisible canvas, and every particle's resting position comes directly from a lit pixel in that bitmap. Change the word, the font, or the size and the particle field regenerates itself — nothing is hand-placed.

02 How the effect works

  • Sampling: the word EMBER is rendered at 900-weight into an offscreen canvas sized to match the visible stage, font-size auto-fit so the text fills 86% of the stage width. getImageData is then walked on a grid every CELL pixels (1–10px, tied to the density slider: CELL = 11 − densitySlider); any sample with alpha > 130 becomes a particle's home coordinate (tx, ty) — a fairly strict cutoff that rejects most anti-aliased edge pixels so the field reads as clean letterforms rather than a soft halo. At the default density (grid step 5px) this yields roughly 2,100 particles on a 920px-wide desktop stage and around 480 on a 390px mobile one.
  • Rest state: each particle starts within an 8px jitter of its home so the word reads as solid immediately, no "explode-in" on load.
  • Repel: every frame, for particles within repelRadius of the pointer, force f = (1 − dist/radius)² is scaled by the strength slider and added to velocity along the pointer→particle direction — quadratic falloff so the push is sharp near the cursor and feathers out toward the radius edge, not a hard cliff.
  • Reassemble: a simple spring pulls every particle back toward its home each frame: v += (home − pos) × springK, where springK ranges 0.02–0.182 across the reassemble-speed slider. Velocity is damped by a factor of 0.90–0.965 per frame (also tied to that slider, so "fast" reassembly is both stiffer and less bouncy). No pointer input at all → the spring alone walks every particle home, which is the "idle" reassembly state; there's no separate timer or state machine.
  • Shatter burst: click/tap or the Shatter button applies a radial impulse power / (dist × 0.04 + 1) outward from the burst origin, so nearby particles get thrown much harder than far ones.
  • Rendering: particles are drawn as small circles; a particle's current speed brightens its color from ember orange to a lighter ember-white and grows its radius slightly, so the moment of shattering visibly "glows" faster-moving material.

04 The screenshot pass

The first headless render worked (no console errors, particles seeded correctly), but reading the actual PNG showed the rest-state word reading as pure TV static rather than a "solid" headline — the alpha-threshold/radius/opacity combination let too much low-alpha, anti-aliased edge noise into the field, and the base opacity floor (0.5) made isolated dots nearly vanish against near-black. Overcorrecting the other direction (denser grid + bigger radius + lower alpha threshold) was worse: re-screenshotting showed the letterforms fully dissolve into one shapeless orange blob with no negative space between strokes or letters. It took three screenshot/adjust cycles to land the actual shipped values — grid step 5px, particle radius 1.0–2.3px, alpha-threshold 130, opacity floor 0.6 — the point where "EMBER" reads cleanly as a word at rest on both the 1440px and 390px captures while still visibly being made of discrete dots. Separately, code inspection (not the screenshot) surfaced a real sync bug: the "N pts" density readout was only ever set once at page load, so it went stale after a window resize rebuilt the particle field with a different count; fixed by moving that DOM write inside buildParticles() itself so every rebuild — resize or slider — refreshes the label.

05 Lift this into your site

To reuse this in another frontend, copy three things from index.html: the buildParticles() function (sampling), the step()/burst() functions (physics), and the draw()/drawStatic() pair (rendering + reduced-motion end state).

  • DOM it expects: a <canvas> sitting inside a sized wrapper element (here .stage) so getBoundingClientRect() gives real, non-zero dimensions — the effect will silently produce zero particles if the canvas's container has no intrinsic size yet at first paint.
  • Constants to tweak: WORD (the string sampled), CELL (particle density), repelRadius / repelStrength (feel of the push), springK / damping (reassembly speed and bounciness).
  • Gotchas: set touch-action:none on the canvas or touch-drag will scroll the page instead of steering the effect; respect prefers-reduced-motion by skipping the animation loop entirely and calling drawStatic() once — a shattering headline is exactly the kind of motion that reduced-motion users are opting out of; and rebuild particles on window resize (and on any dynamic container resize) since tx/ty are baked in screen-space pixels, not relative units.

06 Reproduce it

  1. Draw your text to an offscreen canvas sized to the visible stage; auto-fit the font size to a target width
  2. Read its pixels with getImageData and walk a grid, keeping any sample above an alpha threshold as a particle home
  3. Give each particle a home, a live position (start near-home), and a velocity; simulate a spring pulling live→home every frame
  4. Add a pointer-proximity repel force with falloff so it fights the spring near the cursor, loses further away
  5. Draw particles (not the font) on the visible canvas; provide a static reduced-motion fallback that skips the loop entirely
