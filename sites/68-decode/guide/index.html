DECODE

Text that scrambles before it tells you the truth

01 The idea

Every heading on this page is lying to you for a few hundred milliseconds before it resolves. It's the "decrypted text" trick popularized by libraries like React Bits — a heading cycles through random glyphs and progressively locks into the real characters, left to right, with enough jitter that it reads as a signal being decoded rather than a typewriter effect. It's staged here as a portfolio hero + section headings because that's exactly where this component gets lifted into real sites: it announces a page section without a video, a library, or a single extra asset.

02 How the effect works

  • Per-character spans: each heading's text is split into one <span class="ch"> per character on init. This is what makes independent per-character state possible — you cannot scramble part of a text node.
  • Lock frame per character: character i gets a lock frame of i·0.6 + 3 + random(0,5) (in ticks). The per-character stagger is what makes the reveal sweep left-to-right instead of resolving all at once; the random jitter keeps it from looking like a metronome.
  • The tick loop: a setTimeout chain (not requestAnimationFrame) fires every SPEED ms — a deliberate choice so the "scramble speed" slider maps directly and predictably to wall-clock time, independent of the display's refresh rate. Each tick, every span whose lock frame the running counter hasn't reached yet is reassigned a random character from the active charset; once the counter passes its lock frame, that span snaps to its real character and is marked .locked permanently.
  • Monospace is load-bearing: IBM Plex Mono is used for every decoded heading specifically because glyphs from three completely different charsets (letters, symbols, binary) must swap in and out without changing the heading's total width — a proportional font would make the line visibly jitter and reflow every tick.
  • Two trigger sources, one method: an IntersectionObserver at threshold: 0.4 calls Decoder.run() the first time a heading crosses 40% visible (this is also what fires the hero on page load, since it starts in-view), then immediately unobserves that element — scroll is a one-shot reveal, not a repeat-on-every-pass trigger. A mouseenter listener on the same element calls the identical run() again, gated by the "hover retrigger" toggle. Re-running clears any in-flight setTimeout before restarting, so rapid hovers never stack overlapping decode loops on the same heading.

03 Type & color

IBM Plex Mono (headings, monospace-required) + Inter (body) · near-black #06090a · matrix green accent #4dff88 · dim in-flight scramble green #3a6b52 · amber #f2c14d micro-accent for the status tag and card numbers, kept off the green/near-black axis so it doesn't compete with the decode effect itself

04 The screenshot pass

Two real bugs, two passes. First pass (desktop and mobile both): the hero heading and the section headings were frozen mid-scramble — dim-green nonsense glyphs where real words should be. The screenshot tool settles for under two seconds before capturing, but the original per-character stagger (2.1 ticks/char at 45ms) meant a 30-character headline took roughly 3.4 seconds to fully lock in, comfortably past the capture window. Fixed by cutting the stagger to 0.6 ticks/char with a smaller base offset/jitter, bringing the same headline's full decode under 1.2 seconds.

Second pass: the section headings now resolved cleanly, but the hero — which should have had the most time of any heading, since it starts decoding at page load — was still caught mid-scramble. The actual cause: the screenshot tool walks the whole page top-to-bottom to force lazy content into view, then scrolls back to 0 right before the final capture. That final scroll-to-top made the hero re-enter the viewport, which re-fired its IntersectionObserver callback and restarted its decode with only ~400ms left before capture — nowhere near enough. The observer was retriggering on every scroll-into-view pass instead of once. Fixed by calling io.unobserve(entry.target) right after a heading's first reveal, so the scroll trigger is truly one-shot and only the explicit hover listener can restart it afterward. Re-screenshotted and confirmed the hero and every section heading read as fully locked-in, legible text on both desktop and mobile.

05 Lift this into your site

Copy the Decoder class and the CHARSETS object as-is. It expects: an element with a data-text attribute holding the string to reveal (the element's own text content is discarded and rebuilt as spans, so set the real text there, not as a text node), and the three CSS rules .ch / .ch.scrambling / .ch.locked for color/weight per state. Tunables are plain top-level variables: SPEED (ms per tick — this is what a "scramble speed" slider should write to), CHARSET (swap in your own string of glyphs), and the stagger/jitter constants inside run() if you want a faster or slower left-to-right sweep. To trigger on scroll-into-view, instantiate one IntersectionObserver and call .run() per decoder on intersect, as done here — do not create a separate observer per element, it doesn't scale past a handful of headings. Gotchas: always branch on prefers-reduced-motion and skip straight to the locked state (a scramble loop that never settles is exactly the kind of motion that spec exists to suppress); and use a monospace font, or accept that non-monospace glyph swaps will visibly jitter the line width every tick.

06 Reproduce it

  1. Split the target text into one span per character, storing the real string separately (e.g. as a data attribute)
  2. Compute a staggered, jittered "lock frame" per character index
  3. Run a timed tick loop: before a span's lock frame, assign it a random glyph; at/after, snap to the real character and stop touching it
  4. Wire an IntersectionObserver to call the same run function on scroll-into-view, and a mouseenter listener (behind a toggle) to re-run it on hover
  5. Branch on prefers-reduced-motion to settle instantly to the final text instead of looping
