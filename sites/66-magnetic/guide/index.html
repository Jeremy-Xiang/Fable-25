MAGNETIC

Spring-physics magnetic buttons & icon dock — hand-rolled, no library

01 The idea

Magnetic buttons are one of the most-copied "premium site" tells — a CTA that leans toward your cursor before you've even clicked. Most implementations found in the wild fake the return with a CSS transition: transform 0.3s ease-out, which looks fine on the pull but dead on release: it eases to zero and stops, no life in it. MAGNETIC instead drives the offset with an actual spring-damper each frame, so the release has a small elastic overshoot — the button visibly settles rather than just arriving.

02 How the effect works

  • Distance test: every [data-mag] element re-reads its own getBoundingClientRect() each frame, subtracts its current offset to recover its resting center, then measures dist from that center to the pointer.
  • Falloff: inside the pull radius R, fall = 1 − dist/R (linear falloff to zero at the edge); the pull target is (pointer − center) × strength × fall.
  • Spring integration: each axis runs a semi-implicit Euler spring: acc = k·(target − current) − damp·velocity, then velocity += acc·dt; current += velocity·dt, with k the stiffness slider and damp = 2·√k·0.42 — a damping ratio under 1 on purpose, so the return visibly overshoots and rings once before settling instead of arriving flat.
  • Dock magnification: icons spring a second value, scale, toward 1 + 0.55·fall² inside R, and toward a softer 1 + 0.18·fall2 out to 1.7×R for neighbors. Because every icon runs the identical per-element distance calculation against the same pointer, the macOS-dock-style neighbor lift falls out for free — nothing hard-codes "look left/right at your siblings."
  • Rendering: one style.transform write per element per frame — translate(dx,dy) for buttons, translate(dx, dy − (scale−1)·26) scale(scale) for dock icons (the extra vertical term keeps the icon's growth reading as "lifting up," like a real dock, instead of growing from its own bottom edge).

04 The screenshot pass

The first headless render looked clean — good contrast, no clipped text, mobile held up — but it exposed a real functional gap rather than a visual one: the entire effect is driven by pointermove, so the very first render (and every static screenshot, forever) shows nothing but six inert buttons sitting at rest. A first-time visitor who lands and doesn't immediately wiggle their mouse would have no idea anything on the page reacts to them at all. Fix: an introSweep() that, once on load (skipped under prefers-reduced-motion and on touch devices), synthetically walks the same pointer.x/y state used by real events through each button and dock icon's center 300ms apart, then sets pointer.active = false and steps aside — real pointermove takes over instantly the moment a visitor actually moves their mouse. The re-screenshot after this fix shows the dock's last icon visibly enlarged and lifted mid-sweep, proof the effect now demonstrates itself without needing a real cursor.

05 Lift this into your site

  • Copy: the items array builder, springStep(), and the loop() function — that's the whole engine, framework-free.
  • DOM contract: tag any element data-mag; add data-dock too if you also want the scale/lift behavior (macOS-dock magnification). No wrapper markup required — it reads the element's own rect.
  • Tunables: the three constants RADIUS, STRENGTH, STIFF, plus DAMP_RATIO (keep it under ~0.6 for a visible elastic snap; push toward 1 for a stiffer, more "professional" feel with less bounce).
  • Gotchas: gate the pointer listeners and rAF loop behind matchMedia('(hover: hover) and (pointer: fine)') — on touch there's no hover state to pull toward, so skip the JS entirely and let elements act as plain tappable buttons. Also respect prefers-reduced-motion the same way. Because the loop reads getBoundingClientRect() live every frame, it stays correct through resizes and scrolling with zero extra listeners — don't cache centers once at load, they'll drift stale.

06 Reproduce it

  1. Mark each magnetic element data-mag, and data-dock for scale/lift behavior
  2. Each frame, per element: measure its resting center from getBoundingClientRect() minus its current offset
  3. Compute pointer distance from that center; inside radius R, target = offset × strength × linear falloff
  4. Integrate dx, dy (and scale for dock items) toward that target with an under-damped spring, not a CSS transition
  5. Write a single transform per element; gate the whole loop behind a fine-pointer + no-reduced-motion check
