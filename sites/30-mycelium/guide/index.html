MYCELIUM

A network grows out of the photograph

01 The idea

The brief for this site asked for growth that looks like it's "emerging from the photo" rather than sitting on top of it — so the growth's starting points had to come from the photo, literally. Instead of hand-placing seed coordinates, the page reads the hero image's own pixels at load time, finds the bright cyan-green ones (the glowing threads and mushroom caps, not the dark soil around them), and uses those exact positions as the origins for a recursive branching system. The generative network is answering the photograph, not decorating it.

02 The craft

  • Hero: one nano_banana_pro generation, "bioluminescent mycelium threads and small glowing mushroom caps on dark forest soil, macro, cyan-green glow" — used as a full-bleed object-fit:cover background
  • Seeding: the image is drawn into a hidden 172×96 canvas, every pixel scored by green*1.3 + blue*0.5 − red*0.9 to isolate the glow from the brown/black soil, top-scoring pixels greedily kept while enforcing a minimum spacing so seeds spread across the frame instead of clustering on one mushroom cap
  • Coordinate mapping: seed points are stored as 0–1 normalized image coordinates, then mapped to on-screen pixels using the exact same scale/offset math the browser applies for object-fit:cover — so a seed genuinely lines up with the bright pixel it was sampled from, at any viewport size
  • Growth: each active tip steps forward with a small random heading change every frame, occasionally forking into two tips at a shallower angle and reduced width (capped at depth 7), and retires when its life budget or width runs out — a minimal L-system-flavored rule set, no external library
  • Rendering is additive and never clears — segments accumulate as short strokes with hsla color, so the network looks etched rather than painted, and stays visually consistent with the render cost bounded by a hard cap of 140 concurrent tips
  • Clicking anywhere drops a new spore (three fresh tips at that point), the one deliberate piece of visitor-driven interactivity beyond the ambient growth

03 Type & color

Familjen Grotesk (display/body) + Martian Mono (HUD/labels) · near-black #05070a · bioluminescent green #7cffb2 · teal glow #4dffe0

04 Reproduce it

  1. Draw the source image into an offscreen canvas and read its pixel data with getImageData — score pixels by the channel combination that matches your subject's glow, not just raw brightness
  2. Greedily select high-scoring pixels while enforcing a minimum pairwise distance, so seeds spread rather than pile up on the single brightest spot
  3. Re-derive the same object-fit:cover scale/offset math in JS to convert normalized image coordinates back to screen pixels — this is what keeps generated elements visually locked to the photo under it
  4. Keep the branching rule set tiny: step, jitter the heading, occasionally fork with reduced width, retire past a life or width threshold — complexity emerges from repetition, not from the rule itself
  5. Cap total active tips with a hard ceiling so the simulation is self-limiting instead of needing a manual stop condition

05 Iteration passes

Build pass: the first pixel-scoring pass used raw luminance, which also picked up bright specular highlights on wet dead leaves — switching to the green/blue-weighted, red-penalized score above cleanly isolated the bioluminescent pixels from the rest of the frame.

Code-review pass: the canvas pixel read is wrapped in try/catch with a hardcoded normalized fallback point set, so a blocked cross-origin canvas (e.g. opening the file directly rather than through a server) degrades to a fixed, still-reasonable seed layout instead of throwing and leaving the hero blank. Verified the growth loop is requestAnimationFrame-only under normal motion and fully replaced by a synchronous "fast-forward to completion" pass under prefers-reduced-motion, so a reduced-motion visitor sees the finished network immediately with no animation loop running at all.

Live-browser pass: served locally; on first paint before the image finished decoding, the canvas briefly rendered against a 0×0 sizing on some reloads — moved the seeding and resize call into the image's load handler (with an immediate check for img.complete as a fallback for cached loads) so seeding always runs against real pixel data.
