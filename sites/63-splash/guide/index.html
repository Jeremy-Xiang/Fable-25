SPLASH

A hand-rolled dye-splash cursor trail — no WebGL, no fluid library, staged as a portfolio hero

01 The idea

React Bits' "Splash Cursor" is one of the most-copied premium interactions in creative portfolios: a fluid, ink-like trail that blooms and swirls behind the pointer. Most implementations lean on a full WebGL stable-fluids solver (Pavel Dobryakov's classic webgl-fluid-simulation). SPLASH gets the same visual language — advecting dye, curling turbulence, additive glow, gradual dissipation — from a coarse 2D-canvas grid simulation instead, so it can drop into any page without a shader pipeline.

02 How the effect works

The simulation runs on a low-resolution grid (110 cells wide, height derived from the hero's aspect ratio and clamped to 50–160 cells) holding two fields as flat Float32Arrays: velocity (vx, vy) and dye density (dr, dg, db). Every animation frame runs five steps in stepSim(dt):

  • Curl-noise turbulence: a scalar potential noiseP(x,y,t) = sin(0.09x+0.8t)·cos(0.07y−0.6t) + 0.6·sin(0.05(x−y)+0.35t) is differentiated with a central finite difference (step 0.6) to get its perpendicular gradient — curlX = ∂noiseP/∂y, curlY = −∂noiseP/∂x. That's the standard curl-noise construction: because it's built from a gradient rotated 90°, the resulting force field is divergence-free by definition, which is what makes the flow swirl instead of just pushing dye outward.
  • Semi-Lagrangian advection: instead of pushing dye forward (which is unstable at large steps), each cell asks "where did my content come from?" — it steps backward along the velocity field (x − vx·dt·5.2) and bilinearly samples the field at that point via sample(). Velocity is advected through itself first, then dye is advected through the freshly-updated velocity.
  • Viscosity: a cheap 4-neighbor blur (86% self / 14% neighbor average) is blended into the velocity field each step, which is what keeps the swirls smooth rather than noisy.
  • Dissipation: both fields are multiplied by a decay factor every step — velocity by a fixed 0.985, dye by 1 − (0.0004 + (dissipation/100)² · 0.05), a quadratic map chosen so the default setting lingers for several seconds while the top of the slider wipes the canvas in about a second.
  • Splats: pointer/touch movement calls addSplat(px, py, vdx, vdy, strength, hueDeg), which adds velocity and an HSL-derived color into every grid cell within the splat radius, weighted by a Gaussian falloff exp(−d²/(r²·0.5)).

The dye grid is written into a tiny offscreen canvas via putImageData, then drawn scaled up onto a full-size offscreen buffer with globalCompositeOperation = 'lighter' (additive blending — overlapping splats brighten rather than occlude, like real light/dye) plus a second, blurred, half-opacity pass for bloom. That buffer is pushed to the visible canvas with one drawImage call per frame.

04 The screenshot pass

The first headless render came back solid black — the canvas was there, the JS was running, but no dye was visible. Digging in with an instrumented copy of the screenshot harness (reading the canvas back with getImageData right before capture) found a real, specific bug: the intro demo only fired six widely-scattered splats, and the default dissipation curve decayed them to near-zero within about 1.5 seconds — while the idle "ambient replenishment" splat was keyed off lastMoveTime = 0, so its first fire didn't land until roughly 2.6 seconds of page life. That left a genuine dead window between "intro splash gone" and "ambient splash not yet born" — and a ~1.7–1.8s post-load capture (the harness's fixed wait plus its full-page scroll pass) landed squarely inside it. Fixed by clustering nine intro splats centrally so they reinforce each other, slowing the dissipation curve (see §02), and giving the ambient timer an early first fire at 1.1s instead of 2.6s.

A second, separate finding surfaced while chasing residual flakiness: repeated identical runs against this repo's real path (which contains a literal space, "Claude Sites") intermittently still screenshotted black, even though getImageData confirmed bright pixels were present in the canvas at the exact instant of capture. A controlled test — the same file, byte-for-byte, served from a path with no space and from the same real path with the space percent-encoded (%20) — rendered correctly on every run; the raw, unencoded space was the reproducible variable. That's a headless Chrome/puppeteer file://-URL quirk external to this page's code (verified with disposable test pages containing no simulation logic at all), not something fixable from within sites/63-splash/index.html. The frame is still double-buffered (see §02) as sound practice regardless, since a canvas that's only ever updated with one atomic drawImage is easier to reason about than one built from several draws in sequence.

05 Lift this into your site

Everything needed lives between the <canvas id="splash"> element and the closing </script> — copy that whole block plus the CSS on canvas#splash (it must be position:absolute;inset:0 inside a position:relative parent that defines the stage's size, plus touch-action:none).

  • Functions to copy as a unit: allocSim, resize, noiseP/curlX/curlY, sample, hslToRgb, addSplat, stepSim, renderSim, plus the pointer listeners and the reduceMotion branch at the bottom. They share module-level state (vx/vy/dr/dg/db, CFG), so they aren't independently separable.
  • The staged copy is fake: "Arden Cole" is a fictional placeholder persona invented to make the hero look like a real portfolio — no reference to any real person. Swap the name, role line, and links for your own when you lift the block.
  • DOM contract: one <canvas> inside a sized, positioned container (heroWrap in the code — rename the document.querySelector('.hero-wrap') line to match your container).
  • Tunable surface: the CFG object (dissipation, splatRadius, hue, curlForce) — wire your own controls to it, or hardcode values and delete the panel. SIM_W (default 110) trades resolution for performance; the bloom blur radius (9px in renderSim) is the next thing to turn down on low-power devices.
  • Gotchas: canvas needs touch-action:none or touch drags will scroll the page instead of painting; always resize and reallocate the sim grid together (resize() calls allocSim()) — resizing the canvas without rebuilding the arrays will misalign every index; respect prefers-reduced-motion by settling to one rendered frame and driving further updates only from direct pointer events, not a free-running requestAnimationFrame loop (see the reduceMotion branch); and if you screenshot-test this from a script, know that an unencoded space anywhere in the page's file:// path can make headless Chrome intermittently serve a stale compositor frame — percent-encode the path (%20) if you hit unexplained blank captures.

06 Reproduce it

  1. Allocate a coarse grid (velocity + dye, as flat typed arrays) sized to your stage's aspect ratio
  2. Each frame: add a curl-noise force (perpendicular gradient of a smooth potential function) to velocity
  3. Advect velocity through itself, then dye through velocity, via semi-Lagrangian backtrace + bilinear sampling
  4. Dissipate both fields by a per-frame decay factor; blend a touch of neighbor-averaging into velocity for stability
  5. On pointer/touch move, inject a Gaussian-falloff splat of velocity + color into the grid
  6. Render the low-res dye grid to an offscreen buffer, additive-blend it (plus a blurred pass for bloom), then push one complete frame to the visible canvas
