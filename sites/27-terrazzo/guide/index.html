TERRAZZO

A material study you can shake

01 The idea

Terrazzo floors are archives of accident — cement cast around whatever stone and glass was on hand, ground flat, no two chips or two floors alike. That's a nice metaphor for procedural generation, so the site treats the generated macro photo as the "real" material sample and lets a canvas layer keep manufacturing new, never-repeating chips in the same family of colors, forever.

The trick that makes it feel connected rather than bolted-on: the floating chips don't use a hardcoded palette. On load, the page draws the hero image into an offscreen canvas, samples a grid of pixels, filters for saturated (non-cream) ones, and hands that list of real RGB values to the chip generator. Change the hero image and the floating chips would change color with it automatically.

02 The craft

  • Background: the same hero JPEG tiled via CSS background-repeat at a fixed tile size, so it reads as an endless slab rather than one framed photo
  • Live palette extraction: hero image drawn to a 160×90 offscreen canvas, ~4000 random pixel samples filtered by saturation & brightness to reject the cream cement background, first handful of surviving colors kept as the working palette (wrapped in try/catch — falls back to four preset swatches if canvas read access is ever blocked, e.g. opening the file directly instead of via a server)
  • Chips: irregular 6–8 point polygons (not circles) generated per chip so they read as broken stone rather than confetti dots, each with a soft white specular ellipse to match the glossy resin look in the photo
  • Motion: scroll position drives a per-chip parallax offset (each chip has its own depth factor), and cursor proximity pushes nearby chips a few pixels away — both are direct position math, no physics engine
  • "Shake the jar" button re-randomizes every chip's position in one call, a discrete, non-looping interaction that works identically with reduced motion on

03 Type & color

Lilita One (display) + Quicksand (body) · cream cement #f7edd9 · ink #231c3a · plus a 4-color palette sampled live from the hero image at runtime (rose, teal, gold, ember by default)

04 Reproduce it

  1. Tile the source image as a CSS background instead of stretching it — repetition is what makes a "material" read as endless
  2. Draw the same image into a small offscreen canvas and sample random pixels to build a runtime color palette instead of hardcoding hex values
  3. Generate irregular polygons (not perfect circles) for anything meant to look like a natural chip or fragment
  4. Separate "depth" (scroll parallax factor) from "position" per particle so a single scroll listener can drive dozens of independent-feeling layers
  5. Always wrap canvas pixel reads in a try/catch with a hardcoded fallback palette — cross-origin or file:// access can silently taint the canvas

05 Iteration passes

Build pass: the first draft sampled colors but never filtered by saturation, so the palette kept picking near-white cement pixels and the chips looked washed out. Added a saturation threshold (>0.28) and a minimum brightness floor, which reliably isolates the four ink colors now.

Code-review pass: the cursor-repulsion math ran even when reduced motion was on, so hover would still visibly nudge chips despite the setting — moved the position update out of the animation loop entirely for that branch so a static frame really is static. Verified swatch card contrast (dark ink text on white cards) and headline shadow-offset text still meet contrast against the cream background at all breakpoints.

Live-browser pass: served locally; on first load before the async palette sample resolves, the swatch list now renders the fallback palette immediately instead of sitting empty, closing a half-second flash of missing content that showed up when testing on a throttled connection.
