ORRERY

A clockwork solar system you can turn

01 The idea

This is one of Wing II's three pure-3D showcase pieces — no generated asset at all, per the brief. Five brass "worlds," named for Latin metals (Ferrum, Cuprum, Aurum, Argentum, Stannum), orbit a candlelit sun on tilted, gear-marked rings, the way a real armillary orrery is built: tiltable rings nested inside each other, not planets floating in flat space. Every surface — brass, bronze, the sun's glow — is painted procedurally in canvas at runtime.

02 The craft

  • Three.js loaded via an import map (unpkg.com/three@0.160.0), same pattern as 02-monolith in Wing I, plus OrbitControls from the examples/addons path for damped drag-to-orbit and pinch/scroll zoom
  • Procedural brass: a small canvas is painted per-planet with hundreds of randomized translucent dots and fine scratch lines in a hue-shifted palette, then used as a CanvasTexture — no image file, no external texture, five distinct metal tones from one function
  • Each world orbits via a tilted THREE.Group (the "ring") containing a pivot Object3D that rotates on its Y axis every frame; the planet mesh sits offset from that pivot at the orbit radius — the standard, physically-legible way to animate orbital motion in a scene graph
  • Orbit rings are visible TorusGeometry meshes in bronze, with 48 InstancedMesh gear-tick boxes spaced evenly around each ring — a single draw call per ring for the "engraved" detail
  • Lighting is deliberately minimal: one warm PointLight at the sun with per-frame randomized intensity eased toward a target (candle flicker), plus a dim ambient and a faint rim light — no environment map, no second light rig
  • Clicking a world name lerps OrbitControls.target toward that planet's live world position every frame and dollies the camera to a size-appropriate distance, so "visiting" a world tracks it as it keeps orbiting

03 Type & color

Cinzel (engraved-plate display) + Cormorant (body) + Fragment Mono (labels) · near-black brown #0d0805, brass #c08a3e, bronze #8c5a2b, candlelight #ffb25e

04 Reproduce it

  1. Feature-detect WebGL with a throwaway canvas before importing Three.js at all — no point fetching the library if it can't render
  2. Wrap both the dynamic import() calls and the entire scene-setup block in try/catch; on failure, add a class that swaps in a pure-CSS fallback orrery (concentric rotating rings) and hides the canvas
  3. Also wrap the per-frame requestAnimationFrame callback in its own try/catch so a runtime failure mid-session stops the loop and falls back cleanly instead of spamming errors
  4. Build orbits as tilted-group + pivot + offset-child, not by animating raw x/z coordinates by hand

05 Iteration notes

  • Build pass: first draft had planets glide at scene-flat y=0 with no visible ring geometry, reading as generic floating spheres rather than an orrery; added the tilted torus rings and the instanced gear ticks so the "clockwork armillary" identity actually reads, plus named the worlds after Latin metals to match the material.
  • Code-review pass: added a dedicated WebGL feature-detect that runs before any network request, so a browser with WebGL disabled never even attempts to fetch Three.js; gated all orbital motion and the candle-flicker random walk behind prefers-reduced-motion while leaving OrbitControls drag/zoom fully live, since manual camera movement is user-initiated, not automatic motion; confirmed brass-on-void contrast for the UI text and buttons clears AA.
  • Live-browser pass: served locally in headless Chrome and forced a fallback by throwing inside the render loop — confirmed the CSS orrery swaps in cleanly and the WebGL canvas is hidden, not just covered; also caught that the "focus world" camera dolly could overshoot past minDistance on very small planets, clamped the computed focus distance so it never drops below the controls' configured minimum.
